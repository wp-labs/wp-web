# WarpFusion 与竞品的数据对比

> 数据可信的前提是口径透明。本章先讲「怎么测的」，再给「测出来多少」，最后坦白「哪里不占优」。
> 性能数据为引擎在 NEXMark 合成负载与指定配置下的**自测跑批**，对照组来自阿里云公开发布的《Nexmark 性能白皮书》；结论作**能力参照**，非逐位比较、非生产 SLA 承诺。

---

## 一、测试方法论（请先读这一节）

| 维度 | WarpFusion | Flink OSS | 阿里云实时计算 Flink（VVR） |
|---|---|---|---|
| 版本 | **wp-reactor v2.0.7**（核心运行时，性能跑批口径；配套 WarpFusion 工具链 0.5.x，当期约 0.5.4；当前运行时 2.0.18 / 工具 0.5.6） | **1.20.4** | **vvr-11.5-jdk11-flink-1.20** |
| 数据规模 | 100,000,000 条 / 查询（NEXMark，确定性数据、字节级可重放） | 100,000,000 条 / 查询 | 100,000,000 条 / 查询 |
| 计算资源 | Linux **8 核**（与 VVR 同型号云服务器） | 3 × ecs.g6a.xlarge = 12 vCPU / 48GiB | 8 CU（≈8 vCPU / 32GiB 托管集群） |
| Sink | 本地文件（blackhole 等价） | Blackhole | Blackhole |
| 指标 | 哨兵 EPS（引擎消化速率，整轮均值） | RPS = 输入量 ÷ 用时 | RPS = 输入量 ÷ 用时 |
| 跑批日期 | 2026-08-27（权威轮，晚间复跑、负载干净） | 白皮书发布口径 | 白皮书发布口径 |

**残余不对等（必须承认）**：资源计量口径不同（8 核 vs 8 CU / 3×12 vCPU）；OSS 为三节点集群而 WarpFusion 为单机 8 核。**结论作量级参照，不作生产 SLA 承诺。**

**指标术语**：

| 术语 | 口径 |
|---|---|
| WarpFusion **EPS** | 哨兵四元组 `Σn / (max_emit − min_start)`，引擎消化速率（墙钟口径、剔 ingest 等待与启动开销） |
| 白皮书 **RPS** | 输入数据量 ÷ 用时（Duration ms）；Blackhole 汇（排除外部存储干扰） |
| **RSS_peak** | `ps rss` 100ms 采样峰值 |
| **[clean]** | appended 总量对账 + append_failed / dropped_late / memory_evicted / cursor_gap = 0 |

## 二、总览结论

| 对照基线 | 几何平均领先（头条口径） | 算术平均领先（上限语境） | 逐查询区间 | 结果 |
|---|---:|---:|---|---|
| **Flink OSS** | **24.3×** | 44.7× | 6.06× – 231.49× | 20/20 全面领先 |
| **阿里云 VVR** | **6.8×** | 10.1× | 1.76× – 39.98× | 20/20 全部达 VVR |

**为什么头条用几何均值**：逐查询倍数分布严重右偏——约一半查询落在 1.76×~7.15× 的典型区间，而 q7 / q9 / q16 / q20 等构成右尾长尾。对「提速倍数」这种比率量，几何均值乘性对称、抗离群，回答的是「随便挑一个查询大概快多少倍」；算术均值被少数离群值抬高约 1.5×，只作上限语境。

## 四、几个拉开差距的查询类型

| Query | 语义（对应 WarpFusion 语言原语） | vs OSS | 解读 |
|---|---|---|---|
| q20 | 展开关联（snapshot join） | 231.49× | 逐事件关联侧表，Join 按 key 的 O(1) 时态索引 + 零拷贝列式管线，不随窗口增长退化为扫描 |
| q9 | 中标出价（asof join / 受控延迟关联） | 185.08× | 时点语义是一等语法，`emit at` + 挂起驱动行显式声明触发，无需模拟 |
| q7 | 时段最高出价（match 序列） | 116.74× | 跨事件时序匹配走编译期定型的状态机，而非逐事件解释 |
| q11 | 会话窗口统计（session 窗） | 44.36× | 会话窗口为语言原语 |
| q19 | Top-N（stats 声明式统计） | 46.08× | 声明式聚合编译为执行计划 |
| q16 | 多级窗口聚合 | 54.36× | 同上，stats 原语族 |

作为参照系：白皮书口径下 **VVR 相对 OSS 自身的提升是 3.24×**（本报告按 20 个查询复算几何 3.57×）。也就是说，WarpFusion 是在一个已经做过企业级优化的商用引擎之上，再领先一个身位（同方法论 vs OSS 几何 24.3×）。

**其他现代引擎（公开宣称转述，非同方法论实测，不得与上表并列引用）**：Feldera（增量计算）公开宣称相对 Flink 约 2.2×；RisingWave 公开宣称 2–10×（基准方法存在争议）。二者相对 Flink 属 2–4× 量级——WarpFusion 在同方法论下为 24.3×（几何，vs OSS）。

## 五、已知边界与短板（一并公开）

> **弱势项的标准**：只有「该维度上 WarpFusion 低于 Flink（Flink 有/更强，我们无/更弱）」才算相对 Flink 的弱势项；「自己内部相对最弱的项」（如 q14 仍领先 Flink）不算弱势项。下表只列现状，不把内部相对弱项混称为短板。

| 性质 | 项 | 现状与说明 |
|---|---|---|
| **相对 Flink 的能力缺口**（唯一落后项） | 无 exactly-once / checkpoint | 当前 best-effort，可靠性在路线图。引擎能力维度上唯一落后于 Flink 的项 |
| **最弱优势项**（仍领先，非短板） | q14 vs VVR 仅 1.76× | 仍领先（vs OSS 6.06×）。Calculation 类、字符串处理重，瓶颈在行式 cell 求值，已列为通用能力独立立项 |
| **内部已知问题** | q18 内存（RSS_peak 约 27.9GB @ 100M） | 状态窗随数据量线性增长；无 Flink 同口径 RSS 对照数据，不能据此判定劣于 Flink。wp-reactor v2.0.8 起 spill + 规则级 `max_memory` 已使 30M 规模 q18 RSS 峰值下降约 25% |
| **预期内特征**（非 bug） | q5 / q18 规模退化（30M→100M 为 0.58× / 0.34×） | 窗口状态随数据量增长所致，属状态型查询的预期表现 |
| **口径提示** | 告警落 sink ≠ blackhole | 上文全部吞吐为单查询 blackhole 汇口径（纯算力上限）。真实部署若规则大量触发并落 sink，吞吐会显著低于该口径，请按自身告警率实测 |
| **口径提示** | 多规则混合负载 | 目前无近期权威实测（历史一次测量早于批式向量化落地、已过时，禁止引用） |
| **生态广度** | Connector 与规则库 | 注册表式体系已覆盖 Kafka / MySQL / PostgreSQL / Doris / Elasticsearch / ClickHouse / VictoriaLogs / HTTP / UDP / file / tcp / syslog 等主流通道；广度不及 Flink 数百个社区 connector，规则库暂无社区生态 |

## 六、综合使用成本（TCO）

吞吐只是其中一项。落到团队真正要付的账上：

| 成本项 | Apache Flink | WarpFusion |
|---|---|---|
| 硬件 | 至少 2–3 节点（JobManager + TaskManager + Kafka）+ 磁盘状态存储 | 1 台 8GB 节点起步 |
| 中间件 | Kafka + checkpoint 状态存储 | 零外部依赖 |
| 运维人力 | 专职流工程师维护集群、调 checkpoint / state | 单二进制，普通运维即可 |
| 开发人力 | 数据工程师写 Java / SQL，每条规则一次 job 生命周期 | 分析师写 WFL，热加载生效 |
| 规则迭代 | AI 可加速编写，但验证 + 编译 + 部署 job 周期不变 | 编写 → 内联契约测试 → 热加载，链路最短 |
| 授权 | 开源免费；托管按小时计费 | ELv2：企业内部自用免费，转对外服务需商业授权 |

### 量级估算：十万级 EPS 平台（千条规则、秒级响应、7×24）

按公开市场行情粗算，非报价，未含迁移/学习成本；数字依赖成本结构（人力占大头）而非具体值。

| 成本项（年度） | Flink 自建 | WarpFusion |
|---|---|---|
| 计算资源 | 4 × 8C32G（JM + 3 TM）：约 8 万 | 1 × 8C32G：约 2 万 |
| 消息中间件 | Kafka 3 节点：约 6 万 | 0（直连，无需 Kafka） |
| 状态存储 | 对象存储 / checkpoint：约 1 万 | 0（无 checkpoint） |
| 运维人力 | 流平台工程师 0.5 FTE：约 20 万 | 普通运维 0.1 FTE：约 3 万 |
| 规则开发 | 数据工程师 0.5 FTE：约 20 万 | 分析师 0.3 FTE：约 9 万 |
| **年度合计** | **约 55 万 / 年** | **约 14 万 / 年** |
| **3 年 TCO** | **约 165 万** | **约 42 万** |

> 假设基准（可调）：8C32G 云服务器 2 万/台/年；流平台工程师 40 万/年；数据工程师 40 万/年；安全分析师 30 万/年；SRE / 运维 30 万/年。

**量级结论**：Flink 自建 3 年 TCO 落在**百万量级**（约 150–200 万），WarpFusion 落在**十万量级**（约 40 万），**差距约 4 倍**。三点结构性原因：

1. **人力远大于硬件**——Flink 侧硬件仅占约 27%、人力占约 73%；真正的杠杆是摆脱专职流工程师，而非省服务器；
2. **规则迭代频率放大差距**——每月变更 10 次以上时，热加载 + 自带测试的优势进一步拉开；
3. **规模越小固定开销越难摊薄**——十万级 EPS 下 JobManager + Kafka + 状态存储是刚性支出。
