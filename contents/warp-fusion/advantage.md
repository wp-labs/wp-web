# WarpFusion 的优势在哪里

> 一句话概括：**WarpFusion 用「一台机器、一门语言、一套自带测试的规则、一个能热加载的二进制」，把实时关联检测的综合成本压低一个量级。**
> 展开说，优势分五条线：算力架构、语言表达力、正确性与工程治理、AI 开发闭环、运维与成本。

---

## 一、算力：性能不是调出来的，是砍出来的

NEXMark Q1–Q22 全查询对照（详见同目录 `competitive.md`）中，WarpFusion 相对 Flink OSS 几何平均领先 **24.3×**、相对阿里云实时计算 Flink（VVR）几何平均领先 **6.8×**。领先的根因不在调参，而在架构上砍掉了五样东西：

| 杠杆 | 砍掉了什么 |
|---|---|
| **列式批式向量化** | 逐事件对象分配 + 解释器分发 |
| **数据零拷贝** | Event → Record → DataRecord 的多层拷贝 |
| **内存精确控制** | 窗口数据仅过期且被下游全部消费后才释放；数据预读总量设上限 |
| **Rust vs Java** | JVM GC 停顿 |
| **规则即规划** | 运行期逐事件解释（Stats / Match 编译期定型为执行计划） |

其中「内存精确控制」是**设计纪律而非优化技巧**：窗口数据只有在**既已过期、又被所有消费者确认消费**之后才释放，配合按字节计量的预读预算，内存占用是**可预测、可规划**的，而不是「跑着看」。

核心运行时的具体机制（均可对外陈述）：

| 机制 | 说明 |
|---|---|
| **输入即列式的零拷贝管线** | 数据经 Arrow IPC 进入：传输、窗口存储、输出全程是列式批次，接收端零反序列化，不做逐行编解码 |
| **窗口即订阅者** | 窗口不是被动缓冲区，而是带订阅条件的时序数据持有者；同一数据流可被多个窗口以不同窗口类型订阅、互不干扰 |
| **无锁规则执行** | 每条规则独占一份状态机，无共享锁；窗口写入方与规则读取方之间通知驱动、非忙等 |
| **全链路有界通道** | 管道各段按字节上界串联，背压显式化、可配置、可观测；全局无串行点 |
| **消费感知驱逐** | 批次释放须「事件时间已过期 且 所有下游已确认消费」，慢规则不消费则数据驻留——内存有界，且默认不因驱逐静默丢数据 |
| **Join = 统一的时态键查找** | snapshot / asof / anti / interval 全部归一为「键 + 时间谓词」查找原语；按 key 建列式带时间戳索引，查找 O(1) |
| **确定性护栏** | 事件时间语义冻结 + 确定性输出 ID（内容 SHA-256），性能优化以「不改变任何一条告警输出」为前提，用确定性模拟器逐条对拍验收 |

关键：这些是**单机架构优势**。多节点分布式与高可用属于演进路线图（声明式窗口分布 `partitioned / replicated / local` 已设计），当前版本的能力边界请以 `competitive.md` 的「诚实边界」为准。

### 工程化自测亮点（内部 A/B，供容量规划参考）

| 机制 | 内部实测收益 | 口径 |
|---|---|---|
| 输出路径批式向量化（列批直写 + 批式求值） | q1 端到端 30M：约 2.9M → 4.7M+ EPS | 同机 A/B；NEXMark q1 / 30M / 本地文件汇 |
| 预读字节预算（PrereadBudget） | RSS 峰值 −53%（30M：12.6→5.8GB）；EPS 无回退 | 同机 A/B，对照无预算版本 |
| 消费感知驱逐（ack floor） | RSS 峰值 −68%（21.5→6.8GB）；cursor_gap / memory_evicted = 0 | 无损驱逐（不丢数据） |
| Join 列式多 key 索引 | 窗内 1 万–20 万行按 key 查询提速约 2,000×–30,000× | 内部微基准，对比全窗扫描回退 |
| stats 大键状态 spill | q18 30M RSS 峰值 16.5 → 12.4GB（约 −25%），状态内存有界化 | wp-reactor v2.0.8 vs v2.0.7 同规模对比 |

> 说明：上表为引擎在特定负载与配置下的自测 A/B，非与竞品对比；对外引用请保留「内部实测 + 指定配置」限定。

## 二、表达力：把检测语义做成语言一等公民

WFL 的核心论断：**时序检测、实体建模、数值评分、基线偏离等语义，在主流检测 DSL 里要么靠平台能力、要么靠外部模块，在 WFL 里是语言原语——编译期可检查、运行期可解释**。

### WFL 独有能力（五种 DSL 均无对应，已落地）

OR 分支时序 · 双阶段匹配（`on event` + `on close`）· 一等实体声明 `entity(type, id)` · 数值风险评分 `-> score(expr)` · Join 时点语义一等化（`snapshot` / `asof within` / `anti`）· 规则级资源预算 `limits { max_memory; max_disk }` · 输出契约版本化 `yield target@vN` · Conformance 门禁 · 三文件职责分离（`.wfs` / `.wfl` / `.toml`）· 声明式窗口统计 `stats<dur> [group by] { ... }` 与 `tier` 分档 · 跳窗 `hop(size, slide)` · 受控/延迟关联 `emit at` + `reduce` · 哈希族（`md5` / `sha1` / `sha256` / `hex` / `stable_id`）· `cidr_match` · `top_ties(N)` 并列全输出 · 规则级 `let` · `external()` 外部服务调用（如 Redis Bloom 过滤器查弱口令库）。

### 诚实说明

- 🟡 两项规划能力要如实标注：**分项可解释评分**（`score { item @ weight }` 明细）与**基线偏离的完整语义**（`dur` 窗口 + 持久化）尚未落地，落地前不建议作为选型决定性依据。
- 相对 SPL / KQL 这类通用查询语言，差距已收窄到**通用函数库丰富度**这一设计边界：与 SPL Top50 高频函数对齐率 100%（50/50），并额外覆盖安全检测专有函数族；行保留聚合（eventstats）是有意不做，交给下游 SIEM。

## 三、正确性：从「写完祈祷」到「写完验证」

检测规则的价值取决于正确性，而规则语言的成熟度一半看表达力、一半看能否验证。WFL 把测试写进规则文件里：

```wfl
test full_chain for chain_attack {
  input {
    row(scan, sip = "10.0.0.1", ... action = "syn",        event_time = "2026-01-01T00:00:00Z");
    row(login, sip = "10.0.0.1", ... action = "login_fail", event_time = "2026-01-01T00:00:05Z");
  }
  expect { hits == 1; hit[0].score == 90.0; hit[0].entity_id == "10.0.0.1"; }
}
```

配套的完整闭环与工程治理机制：

| 机制 | 说明 |
|---|---|
| `wfl test` | 内联契约测试：写进 `.wfl` 的 `test ... for ...`，一键验证命中 / 未命中两条路径（秒级反馈） |
| `wfl replay` / `wfl verify` | 历史数据离线回放；新旧规则产出**逐字段对拍** |
| `wfgen` | 按 `.wfg` 场景文件生成带**命中 / 近失 / 未命中**三类样本的数据流 |
| Conformance 门禁 | `test`（内联契约）+ `shuffle`（乱序鲁棒性）+ `scenario verify`（场景对拍）前置为发布门槛 |
| 输出契约版本化 | `yield target@vN` + `meta.contract_version`：下游字段演进可灰度、回滚、审计 |
| 规则级资源预算 | `limits { max_memory; disk_provider; max_disk }`，阻断高基数状态膨胀 |
| 确定性生成与对拍 | `wfgen` 同 count + seed 字节级确定；oracle 用同一套引擎规则对拍，NEXMark 30M 规模多规则与确定性模拟器逐条一致 |

AI 时代的分水岭在验证：**「编写」已可交给 AI，但「验证」与「上线」不能被替代**。WFL 语言表面积小、语义显式、验证秒级反馈，恰好把「生成 → 验证 → 修正」的闭环做到最短——这也是 `wf-skills` 技能包、`wf-rules`（18 条按攻击阶段组织的真实规则语料）与编辑器 LSP 即时校验存在的意义。这套设计正是「AI Native」的立足点，完整论据见同目录 `ai-native.md`。

> 必须守住的边界：**AI 生成 ≠ 免验证**。检测规则出错是静默的（漏报 / 误报不报错），生成的规则必须跑 `wfl test` 并纳入回归。

## 四、开发与运维：规则迭代的最短链路

| 环节 | 通用流计算（Flink 路线） | WarpFusion |
|---|---|---|
| 规则编写 | 数据工程师写 Java / SQL，数百行起 | 分析师写 WFL，一条规则几行声明式代码 |
| 验证 | 需起环境、造数据、部署 job | 内联契约测试，写完即验（秒级） |
| 发布 | 每条规则一次 job：编译 + 部署 + 重启 | **热加载**：`wf reload` / Admin API，不重启引擎 |
| 部署 | 至少 2–3 节点集群 + Kafka + 状态存储 | **单二进制**，一台 8GB 节点起步，零外部依赖 |
| 容量 | 集群运维是常态工作 | 8GB 基准可同时承载约 1000 条规则（容量按规则复杂度实测） |

综合成本的结构性差异（详细估算见同目录 `competitive.md`「综合使用成本」）：以千条规则、十万级 EPS 的中等平台估算，Flink 自建约 **55 万/年**（硬件仅占约 27%，**人力占约 73%**），WarpFusion 约 **14 万/年**，3 年 TCO 差距约 **4 倍**——真正的杠杆是摆脱对专职流工程师的依赖，而不是省服务器。

## 五、诚实的选型建议

**适选**（单机可承载量级 + 需要跨事件/跨窗口关联）：

- 攻击链、行为链、缺失检测、实体行为分析、实时频控、指标异常等**跨事件 / 跨窗口**检测；
- 规则**高频迭代**、改动自带测试与热加载的团队；
- 没有专职流计算工程师、或不想为中等量级养一套 Flink 集群的团队；
- 需要可解释评分、输出契约稳定、规则变更可灰度回滚的场景。

**不适选（请诚实回避）**：

| 场景 | 原因 |
|---|---|
| 多节点高可用 / 分布式容错 | 当前无 exactly-once / checkpoint、无分布式协调——**真正的边界在此，不在吞吐** |
| 交互式分析、行保留聚合 | 有意不做，交下游 SIEM |
| 依赖数百种开箱即用的社区数据源 | 有注册表式 connector 体系（已覆盖 Kafka / MySQL / PostgreSQL / Doris / Elasticsearch / ClickHouse / VictoriaLogs / HTTP / UDP / file / tcp / syslog 等），但广度不及 Flink 十年积累的数百个社区 connector |
| 需要通用数学计算（三角函数等） | 函数库聚焦检测场景 |

> 关于核数扩展（常见误解）：8 核单机已达 NEXMark 单查询 200 万–3100 万 EPS，但不能简单推断「堆到 32 核线性翻倍」——无状态轻查询的瓶颈常在单连接读链供给（加核收益有限），窗口 / join / 状态型重查询才吃多核算力。仓库暂无 32 核实测数据，以上为 8 核特征的推断，需 32 核结论应同方法论实测。
